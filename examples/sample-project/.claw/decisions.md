### ADR-001: 登录模块使用 JWT + Refresh Token

- 状态：`accepted`
- 日期：2026-03-21
- 决策人：用户 + AI
- Supersedes: none

#### 背景

需要在较短交付周期内完成稳定、可扩展的登录能力。

#### 备选方案

1. 服务端 Session - 实现简单，但横向扩展成本更高
2. JWT + Refresh Token - 前后端边界清晰，扩展性更好
3. 第三方 OAuth 托管 - 接入成本超出 MVP 周期

#### 结论

选择 `JWT + Refresh Token`

#### 决策理由

1. 更适合无状态 API 部署
2. 后续接入移动端成本更低
3. 与现有网关鉴权方式兼容

#### 影响

- 正面影响：认证链路清晰，便于后续扩展
- 负面影响：需要处理 token 刷新和吊销
- 迁移或兼容成本：中等

#### 验证方式

- 登录、刷新、登出链路集成测试通过

#### 参考资料

- 内部认证规范 v1

### ADR-002: 限流逻辑从控制器中抽离

- 状态：`accepted`
- 日期：2026-03-28
- 决策人：AI
- Supersedes: none

#### 背景

登录接口的限流逻辑分散在控制器中，导致测试难以隔离。

#### 备选方案

1. 保持现状 - 修改少，但测试耦合严重
2. 抽成独立模块 - 更易 mock 和复用

#### 结论

选择 `抽成独立模块`

#### 决策理由

1. 降低控制器职责
2. 提升测试可控性
3. 后续短信登录也可复用

#### 影响

- 正面影响：测试与限流策略解耦
- 负面影响：多一个依赖注入点
- 迁移或兼容成本：低

#### 验证方式

- 登录控制器单测和集成测试均可独立替换限流实现

#### 参考资料

- `src/lib/rate-limit.ts`
