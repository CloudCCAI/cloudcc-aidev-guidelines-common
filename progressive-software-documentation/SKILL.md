# 渐进式软件文档

把文档作为人、AI与软件之间共享的软件模型。只创建能够明确意图、约束实现、协调协作、提供证据或指导使用的内容，不追求文件数量和形式完整。

## 技能版本

- 当前版本：`1.3.0`
- 更新日期：`2026-08-11`
- 采用语义化版本：不兼容的原则或流程变化升级主版本，向后兼容的能力或规则增加升级次版本，措辞修正和小幅澄清升级修订版本。
- 修改本技能时必须在同一次变更中更新版本和日期；使用Git历史查看具体变更，不在技能中维护重复的更新日志。

## 核心原则

1. 先阅读项目已有规则、代码、测试和文档，再判断是否需要文档变更。
2. 遵循项目已有目录、命名和工具，不另建冲突体系。
   项目没有文档约定时，使用根目录 `README.md` 作为入口，其他必要文档放入 `docs/`；只在出现多个同类文档后再创建分类目录。
3. 从当前任务需要的最少文档开始，真实复杂度出现后再拆分。
4. 不创建空目录、空模板、虚假任务、虚假测试结果或无法维护的索引。
5. 一个事实只设一个权威来源；其他位置只写摘要、示例或链接。
6. 区分目标、设计、实现、验证和运行事实，不用其中一个冒充另一个。
7. 将内容区分为已验证事实、合理推断和待确认问题，不把推测写成事实。
8. 区分计划中的设计和当前已生效的设计，未交付功能不得冒充现有能力。
9. 语义变化时检查相关文档；格式和错字修改不扩大为需求变更。
   用户可见行为、业务规则、权限、系统架构、服务职责、模块边界、重要依赖关系、公共接口、消息格式、数据结构、配置方式、部署方式或运维流程变化通常属于语义变化；纯重构、格式化和不改变行为的性能优化通常不属于。
10. 文档与代码、测试或运行结果冲突时，记录差异并请求有权人员裁决，不静默选择一方。
11. 优先引用可执行契约、Schema、测试、配置和运行证据，避免重复抄写可自动获得的信息。
12. 文档应能被人快速阅读，也应让AI只加载完成当前任务所需的上下文。
13. 开发过程中主动从真实使用场景审视方案，综合考虑交互完整性、性能、数据规模和边界情况，发现明显不合理之处时及时调整或提出确认，同时避免基于无证据的假设过度设计。

## 开发工作流

### 开发前

1. 复述当前目标、范围、约束和假设。
2. 识别当前任务属于咨询、Bug、小型修改、新功能、架构、接口、数据、运维还是使用帮助。
3. 读取与任务直接相关的产品、设计、服务、契约和测试事实，不默认加载全部历史资料。
4. 区分已有行为、期望行为和待确认问题。
5. 检查任务是否产生前述语义变化。不产生语义变化的简单修改，只需说明“无需更新文档”；存在语义变化时，再列出需要新建、更新或仅检查的最小文档集合及原因。
6. 只有当不同答案会实质改变产品范围、业务规则、权限、接口或数据时才请求确认；其他问题采用明确且可逆的假设继续，并在结果中说明。

### 开发中

1. 使用已确认的目标、设计和契约约束实现。
2. 新发现的限制、边界和差异先记录在当前任务上下文或相关现有文档中，不依赖对话记忆；只有具有长期价值时才创建新的长期文档。
3. 实验性方案保持为草案，验证前不写成当前事实。
   同一文档同时包含计划行为和当前行为时，使用“草案”“当前”“历史”等明确章节或标签区分；仍容易误读时，将变更Spec与当前设计分开。
4. 不为了符合模板增加用户未要求的功能和抽象。

### 开发后

1. 执行与变更风险相称的真实测试，并如实报告结果。
2. 对比目标、设计、代码、契约和测试，说明未实现项及偏差。
3. 更新受语义变化影响的当前设计、接口、数据、帮助或运维资料。
4. 保留必要的历史关系，避免旧文档被误认为当前规则。
5. 检查文档入口、内部链接和阅读路径是否仍然有效。

## 常见文档及作用

| 文档 | 主要作用 | 何时需要 |
|---|---|---|
| 项目概述 | 说明问题、用户、目标、范围、术语和系统边界 | 项目缺少统一入口时 |
| Spec | 记录一次变更的背景、目标、范围、非目标和验收标准 | 新功能或重要行为变化时 |
| 功能设计 | 描述计划行为或当前有效的业务规则、流程、状态和异常 | 仅靠Spec无法指导实现时 |
| 场景 | 描述一次业务如何跨角色、服务或外部系统完成 | 跨参与者流程难以理解时 |
| 架构 | 描述系统结构、边界、约束和重要取舍 | 结构影响多个模块或长期维护时 |
| 服务文档 | 描述单个服务的职责、非职责、模块、依赖和运行方式 | 服务内部边界需要独立说明时 |
| API、事件与数据契约 | 定义系统协作所依赖的稳定语义和结构 | 存在共享消费者或兼容责任时 |
| 测试资料 | 将验收标准连接到可执行或可观察的证据 | 需要说明如何验证时 |
| Bug记录 | 记录现象、影响、复现、根因、修复和回归结果 | Issue不足以保存长期知识时 |
| ADR | 保存重要且难以逆转的决策、理由和后果 | 未来维护者需要理解取舍时 |
| 运维文档 | 指导部署、监控、排障、恢复和回滚 | 软件需要长期运行时 |
| 使用手册 | 指导用户使用已经验证并交付的功能 | 功能准备交付或已经发布时 |

这是一张选择表，不是必须创建的目录清单。小项目可以合并相关内容；只有在主题、读者、维护者或生命周期明显不同时才拆分文件。

## 事实与关系

- 产品目标回答“为什么做”。
- Spec回答“这次改变什么、如何验收”。
- 设计回答“准备如何工作”或“当前规则是什么”，并明确其状态。
- 架构与服务文档回答“系统如何划分职责”。
- 机器可读契约回答“系统之间如何协作”。
- 代码和配置回答“当前怎样实现”。
- 测试、日志和指标回答“实际是否符合预期”。
- 使用手册回答“用户现在如何完成任务”。

通过相对链接连接直接依赖的文档，避免复制完整规则。项目文档较多时维护一个根索引，使人和AI能够从产品或功能进入相关设计、服务、契约、测试、运维和帮助资料。

历史Spec用于解释变化过程，当前设计用于说明现行规则。新规则替代旧规则时，应明确标记替代关系和适用范围；不要依赖文件位置猜测哪个版本有效。

## 协作与命名

优先沿用项目已有编号方式。多人并行创建文档时，不使用扫描全局最大编号再加一的方式；可采用“类型-稳定开发者标识-个人序号-简单描述”，例如 `FEAT-xuhm-001-login-timeout`。创建前检查完整标识是否已经存在；简单描述仅用于创建时帮助识别，属于稳定标识的一部分。标识一经被引用，不因标题、路径或负责人变化而修改。

## 图与阅读视图

只在图能比文字更清楚地表达关系、流程、状态、边界或部署时画图。每张图只回答一个主要问题，不追求能够说明全部系统的“终极架构图”。图形源文件应与文档一起管理。

使用本技能生成或更新软件项目的Markdown文档时，必须同步生成或更新一个供人类阅读的对应HTML文件。优先沿用项目已有的生成工具、输出目录和命名约定；没有约定时，在Markdown文件同目录生成同名 `.html` 文件。Markdown是事实来源，HTML是派生阅读视图，不手工编辑。

HTML阅读视图必须以人类快速理解和定位重点为目标，不得只做无样式的格式转换：

- 在页面开头提供仅从Markdown提炼的阅读摘要，优先呈现文档目的、关键结论或当前状态，以及实际存在的风险、待确认事项和下一步；不补造源文档没有的信息。
- 使用语义化HTML，并保持连续、清晰的标题层级；长文生成可跳转目录，将相关内容组织为明确分区，避免大段无结构正文。
- 使用易读的字号、行宽、对比度、留白、列表和表格；用醒目但不过度的提示区突出关键结论、风险和注意事项，不仅依赖颜色表达含义。

## 完成检查

完成文档相关工作前确认：

- 只创建或修改了当前任务真正需要的文件。
- 目标、当前行为、期望行为和验收标准没有混淆。
- 已验证、推断和待确认内容能够被识别。
- 每个重要事实都有明确且唯一的权威来源。
- 代码、契约、测试和文档不存在未说明的冲突。
- 未执行的测试没有被写成通过。
- 语义变化已经同步到直接受影响的长期文档。
- 历史文档不会被误认为当前规则。
- 新成员和AI能够从项目入口找到完成任务所需的文档。
- 每个新增或更新的Markdown文档都有同步的HTML阅读视图。

结束时简要报告本次使用的事实来源、修改的文档、验证结果和仍待确认的问题。
