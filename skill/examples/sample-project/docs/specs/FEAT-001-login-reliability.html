背景与目标

⌄
  • 登录失败路径的集成测试在 CI 中偶发返回 429，导致结果不稳定
  • 本次交付目标是让失败路径的错误结构和状态码稳定、可测试、可回归
  • 修复完成后，登录相关回归不应再受测试环境限流共享状态影响

范围

⌄

In Scope

  • 梳理登录失败路径返回结构
  • 抽离或隔离测试环境中的限流依赖
  • 补齐登录失败路径的集成测试

Out Of Scope

  • 登录成功路径的新功能扩展
  • 第三方登录或 SSO 集成
  • 生产环境限流策略重构

用户场景

⌄
  • 当用户输入错误密码时，接口应稳定返回 401
  • 当测试反复执行登录失败用例时，不应因为共享限流状态而偶发返回 429
  • 当真实限流触发时，接口仍应保持统一错误结构

现状与约束

⌄
  • 当前限流逻辑已从控制器中抽离到独立模块
  • 测试环境复用 Redis key，造成失败路径与限流状态耦合
  • 需要在较小改动范围内完成修复，避免影响现有登录成功链路

方案设计

⌄
  • 维持当前 JWT + Refresh Token 认证方案不变
  • 对登录失败路径的测试场景隔离限流存储，实现可控 mock 或 reset
  • 保持登录接口统一响应结构 { code, message, data }

接口与数据影响

⌄
  • 对外 API 路径和字段保持不变
  • 测试环境的限流存储策略需要增加隔离或重置能力
  • 不引入新的数据库字段或迁移

任务拆分

⌄
  • TASK-001：稳定登录失败路径并补齐测试
  • 如果修复后还需要回归检查，可追加 qa-agent 负责的 review 任务

验收标准

⌄
  • 错误密码场景稳定返回 401
  • 限流场景返回 429 时结构与规范一致
  • npm run test:integration 连续运行不再出现偶发失败
  • test-report.md 记录最新真实结果

风险与回滚

⌄
  • 风险：对限流隔离方式处理不当，可能掩盖真实限流逻辑问题
  • 风险：mock 范围过大，可能降低集成测试真实性
  • 回滚：恢复限流依赖注入前的实现，并在 issue-list.md 中保留未解决状态
